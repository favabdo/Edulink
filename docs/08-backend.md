# الباك اند — Eduspace API

> الكود في `eduspace-web/api` — **ASP.NET Core Web API (.NET 10)**.
> دليل التشغيل ونقاط النهاية في `eduspace-web/api/README.md`.

---

## 1) التقنية والقرارات

| البند | القرار | السبب |
|---|---|---|
| الإطار | **ASP.NET Core (.NET 10)** | يتكامل أصلًا مع SQL Server (الهدف النهائي)، أداء عالٍ، ويعمل على Linux VPS |
| الوصول للبيانات | **EF Core** | يُتيح تبديل المحرّك (PostgreSQL ↔ SQL Server) بتغيير سطر واحد دون تغيير الكود |
| المخطط | **`db/schema.sql` فقط** | EF Migrations **ممنوعة** — المخطط ملف واحد تراكمي كما اتفقنا |
| التجزئة | **bcrypt** (`BCrypt.Net-Next`) | التجزئة في التطبيق لا في القاعدة، لأن SQL Server لا يملك دوال تجزئة مكافئة |
| الجلسات | **توكن مخزَّن في عمود `token`** | مطابق لتصميم جدول `Edu_Users` المتفق عليه |
| التطوير المحلي | **SQLite** | يشغّل التطبيق كاملًا بلا أي خدمة خارجية |

### تبديل محرّك قاعدة البيانات

كل الفرق في الإعدادات، لا في الكود:

```jsonc
"Database": {
  "Provider": "Sqlite",      // للتطوير المحلي (ينشئ الجداول من الكيانات)
  "EnsureCreated": true
}
// "Provider": "Postgres"   // Supabase — مع EnsureCreated = false
// "Provider": "SqlServer"  // سيرفر الشركة لاحقًا (تُضاف الحزمة عند الحاجة)
```

### لماذا SQLite في التطوير؟

لأنه يسمح بتشغيل المكدس كاملًا واختباره فعليًا بلا انتظار؛ Supabase تبقى للإعداد الحقيقي.
**مهم:** هذا لا يخالف قاعدة «ملف مخطط واحد» — الجداول الحقيقية تُنشأ من `db/schema.sql` فقط،
وSQLite يُنشئ نسخته المحلية من نموذج الكيانات، ولا يُلمس أي قاعدة إنتاج.

## 3) تدفق تسجيل الدخول

```
المستخدم يدخل البريد وكلمة المرور
        ↓
POST /api/auth/login
        ↓
البحث عن الحساب بالبريد (بحروف صغيرة) → التحقق من bcrypt
        ↓
access = 0 ؟  →  403 «الحساب غير مفعّل» (لا يدخل إطلاقًا)
        ↓
توليد توكن عشوائي 256-bit وحفظه في عمود token
        ↓
الواجهة تحفظه في localStorage وتوجّه المستخدم للوحة
        ↓
كل طلب بعدها: Authorization: Bearer <token>
        ↓
TokenAuthenticationHandler يبحث بالتوكن (فيه فهرس) ويبني هوية المستخدم ودوره
```

**عند فتح التطبيق:** الواجهة تنادي `/api/auth/me` بالتوكن المحفوظ — فإن كان ملغيًا أو غير صالح تُمسح الجلسة ويُعاد المستخدم لصفحة الدخول.

## 4) الصفحة الداخلية (اللوحة)

بُنيت مطابقة للصورة المرجعية التي أرسلها صاحب المشروع:

- **شريط علوي:** الشعار في بداية السطر (يمين في العربية)، وحساب المستخدم والإشعارات والمظهر واللغة في النهاية.
- **شريط جانبي:** الرئيسية · جدولي اليومي · حصصي · الطلاب · التقارير · الرسائل · الإعدادات + بطاقة اقتباس أسفله.
- **بانر ترحيبي** باسم المستخدم الحقيقي من `/api/auth/me` ودوره.
- **جدول الحصص اليومي** · **أدوات سريعة** · **ملخص اليوم** · **الحصص القادمة** · **النشاط الأخير**.

### ما هو حقيقي وما هو تجريبي

| العنصر | المصدر |
|---|---|
| اسم المستخدم ودوره | ✅ **حقيقي** من قاعدة البيانات |
| الحصص والطلاب والتقارير والنشاط | 🔶 **بيانات تجريبية ثابتة** في `src/pages/Dashboard/dashboardContent.ts` |

الجداول المرتبطة (الحصص، الطلاب، المواعيد، الإشعارات) **لم تُبنَ بعد**، فالصفحة تعرض بيانات تجريبية، ويظهر تنبيه بذلك أسفل جدول الحصص.

### انحراف مقصود عن الصورة المرجعية

الصورة المرجعية تُظهر الشريط الجانبي على **اليسار** مع نصوص عربية RTL. بُني على **اليمين** (بداية السطر في RTL) لأنه الموضع الطبيعي لتصفح عربي، ومتسق مع باقي الصفحة (الشعار في اليمين، النص محاذى لليمين).
**تبديله لليسار تغيير سطر واحد** لو أراد صاحب المشروع مطابقة الصورة حرفيًا.
