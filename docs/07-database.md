# قاعدة البيانات — القواعد والتصميم

> **ملف قاعدة البيانات الوحيد:** `database/schema.sql`
> ودليل تشغيله السريع في `database/README.md`.

---

## 1) قواعد إلزامية معتمدة (طلب صاحب المشروع)

1. **ملف واحد لكل تغييرات البيانات** — أي جدول أو عمود أو فهرس جديد يُضاف إلى `schema.sql` نفسه، في قسم «إضافات جديدة». الملف **تراكمي**: كل ما زاد حجمه لا يُقسَّم ولا تُنشأ ملفات migrations منفصلة.
2. **قابل لإعادة التشغيل** — كل عبارة محميّة بـ `IF NOT EXISTS` / `DROP IF EXISTS`، فيُشغَّل مرة واحدة أو عشر مرات بنفس النتيجة. (طلب صاحب المشروع: «أعمله رن مرة واحدة».)
3. **اسم كل جدول يبدأ بـ `Edu_`** ثم اسم الجدول: `Edu_Users`, `Edu_Sessions` ...
4. **التشغيل الآن على Supabase** (PostgreSQL)، **ومستقبلاً على SQL Server** الخاص بالشركة.

> القاعدتان 1 و3 مكتوبتان أيضًا في `AGENTS.md` ليقرأهما أي عمل قادم على المشروع تلقائيًا.

---

## 2) استراتيجية محرّكَي القاعدة (Supabase ثم SQL Server)

**المشكلة:** Supabase = PostgreSQL، وSQL Server = T-SQL، وصيغة `CREATE TABLE` بينهما **مختلفة فعليًا** — لذلك لا يمكن لملف SQL واحد أن يعمل على المحرّكين بلا تعديل. الفروق كلها محصورة في:

| البند | PostgreSQL (الآن) | SQL Server (المستقبل) |
|---|---|---|
| المفتاح التلقائي | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `BIGINT IDENTITY(1,1)` |
| نوع الوقت | `TIMESTAMPTZ` | `DATETIME2` |
| النص الطويل | `TEXT` | `NVARCHAR(MAX)` |
| القيم الافتراضية | `DEFAULT 0` مضمّن في العمود | `CONSTRAINT df_... DEFAULT 0` |
| حماية الإنشاء | `CREATE TABLE IF NOT EXISTS` | `IF OBJECT_ID('...','U') IS NULL` |
| تحديث `updated_at` | تريجر `BEFORE UPDATE` | تريجر `AFTER UPDATE` |

**الحل المعتمد:** ملف **واحد** فيه قسم PostgreSQL هو **المُنفَّذ فعليًا**، وقسم **SQL Server كامل مُعلَّق** في آخر نفس الملف. عند الانتقال تُزال التعليقات ويُشغَّل. بهذا يبقى كل شيء في مكان واحد ✓ (كما طلب صاحب المشروع).

**الأعمدة والقيود والفهارس وأسماؤها متطابقة بين المحرّكين** — لا تتغير عند الانتقال.

## 3) جدول `Edu_Users`

يمثل **موظفي المنصة** (لا الطلاب): المدرسون، المشرفون، المديرون، والأونر.

| العمود | النوع | الوصف |
|---|---|---|
| `id` | `BIGINT` | مفتاح أساسي **تلقائي** |
| `name` | `VARCHAR(255)` | الاسم الكامل |
| `email` | `VARCHAR(255)` | فريد، ويُخزَّن بحروف صغيرة (lowercase) |
| `password` | `VARCHAR(255)` | **هاش** كلمة المرور — لا يُخزَّن النص الصريح أبدًا |
| `role` | `SMALLINT` | **0 = مدرس · 1 = مشرف · 2 = مدير · 3 = أونر** (يزيد كلما ارتفع الدور) |
| `token` | `TEXT` | توكن الدخول الحالي — `NULL` = لا توجد جلسة |
| `states` | `SMALLINT` | `0` = الحساب **غير ظاهر للناس** · `1` = ظاهر |
| `access` | `SMALLINT` | `0` = **غير مفعّل، لا يستطيع الدخول للمنصة إطلاقًا** · `1` = مفعّل |
| `img_url` | `TEXT` | رابط صورة المستخدم إن وُجدت — `NULL` = لا توجد صورة |
| `notifications` | `SMALLINT` | **هل إنشاء هذا المستخدم أُرسل كإشعار للكل**: `0` = لا · `1` = نعم |
| `created_at` | `TIMESTAMPTZ` | تاريخ الإنشاء |
| `updated_at` | `TIMESTAMPTZ` | تاريخ آخر تعديل — يُحدَّث **تلقائيًا** بتريجر |

**فهارس:** على `token` (يُقرأ في كل طلب مصادقة) وعلى `role` (تقارير وتصفية).
**قيود:** `email` فريد، وكل الأعلام (states/access/notifications) محصورة في `0 أو 1`.

> ✅ **تصحيح مهم لمعنى `notifications`:** في نسخة سابقة كُتب أنه «إشعارات بانتظار المستخدم» — وهذا **خطأ**. المعنى الصحيح كما أوضحه صاحب المشروع: **هل إنشاء هذا السجل تحديدًا أُرسل إشعار للكل أم لا**. وهو ليس صندوق إشعارات للمستخدم.

---

## 4) جدول `Edu_Students`

يمثل **الطلاب**. نفس بنية الحساب في `Edu_Users` ما عدا:

- **لا يوجد عمود `role`** — كل صف في هذا الجدول طالب (ولي الأمر له جدول مستقل).
- باقي الأعمدة متطابقة: `id`, **`name`**, `email` (فريد), `password` (هاش), `token`, `states`, `access`, `img_url`, `notifications`, `created_at`, `updated_at`.

نفس الفهارس (`token`) ونفس القيود ونفس تريجر `updated_at` (يُعاد استخدام الدالة `Edu_SetUpdatedAt()` نفسها).

> ⚠️ **البريد فريد داخل كل جدول على حدة.** هل يُمنع نفس البريد من أن يكون مدرسًا وطالبًا في نفس الوقت؟ **سؤال مفتوح** لم يُحسم، ولذلك لم نضع فهرسًا فريدًا مشتركًا بين الجدولين.

---

## 5) جدول `Edu_Parents`

**نفس أعمدة `Edu_Students` بالظبط** — بطلب صاحب المشروع:

`id`, **`name`**, `email` (فريد), `password` (هاش), `token`, `states`, `access`, `img_url`, `notifications`, `created_at`, `updated_at`

ونفس الفهرس على `token` ونفس القيود ونفس تريجر `updated_at`. **بدون `role`** (كل صف هنا ولي أمر).

---

## 6) جدول `Edu_Relations` — الربط بين الطالب وولي الأمر

> الاسم السابق للجدول كان `Edu_StudentParents`، وتمت إعادة تسميته إلى **`Edu_Relations`** بطلب صاحب المشروع.

### لماذا جدول ربط منفصل؟

العلاقة بين الطالب وولي الأمر **متعدد لمتعدد (Many-to-Many)**، وليست واحد لمتعدد:

- **ولي أمر واحد قد يكون له أكثر من طالب** — أخوان مسجّلان على المنصة (حالة شائعة جدًا).
- **الطالب الواحد قد يكون له أكثر من ولي أمر** — الأب والأم مسجّلان كلاهما (حالة شائعة كذلك).

ولو خزّنّا الربط في أحد الجدولين لخسرنا أحد الاتجاهين:
- `parent_id` داخل `Edu_Students` ← يقبل **ولي أمر واحد فقط** لكل طالب ✗
- `student_id` داخل `Edu_Parents` ← يقبل **طالبًا واحدًا فقط** لكل ولي أمر ✗

فالاختيار الصحيح — وهو ما اقترحه صاحب المشروع — **جدول ربط مستقل**. ✅

```
Edu_Students ──< Edu_Relations >── Edu_Parents
```

### الأعمدة ومبرّر كل واحد

| العمود | النوع | لماذا |
|---|---|---|
| `id` | `BIGINT` تلقائي | نفس نمط كل جداول المشروع |
| `student_id` | `BIGINT` مفتاح خارجي → `Edu_Students` | طرف العلاقة الأول |
| `parent_id` | `BIGINT` مفتاح خارجي → `Edu_Parents` | طرف العلاقة الثاني |
| `relation` | `SMALLINT` | **صلة القرابة**: `0` = أب · `1` = أم · `2` = وصي/ولي أمر · `3` = أخرى — لأن الارتباط له نوع، ويُعرض للمستخدم («والد الطالب» / «والدة الطالب») |
| `is_primary` | `SMALLINT` | **ولي الأمر الأساسي** — `1` = هو أول من يُتواصل معه. ضروري عند وجود أكثر من ولي أمر لنفس الطالب |
| `states` | `SMALLINT` | `0` = الرابط موقوف · `1` = فعّال — لإيقاف ارتباط دون حذف تاريخه |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | نفس نمط المشروع، مع تريجر التحديث التلقائي |

> ⚠️ **لا يوجد عمود `name` في هذا الجدول** — بطلب صاحب المشروع: `name` أُضيف لكل الجداول **ما عدا جدول الربط**، لأنه ربط بين سجلين وليس كيانًا له اسم.

### القيود (Integrity) — وهي الجزء الأهم

| القيد | الفائدة |
|---|---|
| `UNIQUE (student_id, parent_id)` | يمنع ربط نفس الطالب بنفس ولي الأمر مرتين |
| فهرس فريد جزئي على `student_id WHERE is_primary = 1` | **ولي أمر أساسي واحد فقط لكل طالب** — يمنع وجود اثنين «أساسيين» وهو ما لا معنى له |
| `FOREIGN KEY ... ON DELETE CASCADE` | حذف الطالب أو ولي الأمر يحذف روابطه تلقائيًا فلا تبقى صفوف معلّقة |
| فهرس على `student_id` وفهرس على `parent_id` | البحث في الاتجاهين: «أولياء أمور هذا الطالب» و«أبناء ولي الأمر هذا» |

### قرارات اتُّخذت (وقابلة للتغيير)

1. **لا يوجد عمود `notifications` في جدول الربط** — عن قصد. معنى العمود في بقية الجداول «هل أُعلن الإنشاء للكل»، والربط بين سجلين **ليس حدثًا يُعلَن لكل المنصة**. لو أردت العمود للتوحيد فقط، يُضاف.
2. **`states` افتراضيه `1` هنا** بخلاف جداول الحسابات (افتراضيها `0`). السبب: الحساب يبدأ غير مرئي حتى الموافقة، أما الربط فيُنشئه المشرف فيكون فعّالًا من لحظته.
3. **«ولي أمر أساسي واحد»** قاعدة أضفتها لأن تعدّد «الأساسي» بلا معنى. لو تريد السماح بأكثر من أساسي (حالة الأب والأم منفصلين بسلطة متساوية) نُسقط الفهرس الجزئي.
4. **الحذف المتتالي (CASCADE)** اختير لمنع الصفوف المعلّقة. لو السياسة عندك «لا تُحذف الحسابات بل تُوقَّف» فلن يعمل الحذف أصلًا، ويبقى القيد أمانًا احتياطيًا.

## 7) قرارات مهمة

1. **التجزئة في التطبيق لا في القاعدة.** استُخدم عمود `password` لتخزين هاش **bcrypt** (أو PBKDF2 من ASP.NET Core Identity) لأنه لا يمكن الاعتماد على `pgcrypto` الآن ثم إعادة كتابته على SQL Server — SQL Server لا يملك دوال تجزئة مكافئة. **عمود `password` لا يحمل نصًّا صريحًا أبدًا.**
2. **حالة الأحرف محفوظة.** الأسماء مكتوبة بين تنصيص `"Edu_Users"` لتظهر `PascalCase` كما ستكون على SQL Server. الثمن: يجب تنصيص الاسم في PostgreSQL دائمًا.
3. ✅ **`notifications` ليس صندوق إشعارات.** معناه: **هل إنشاء هذا السجل أُرسل كإشعار للكل**. لذلك لا يحتاج جدول إشعارات ليحلّ محله — وظيفته مختلفة تمامًا. (كان موصوفًا خطأً في نسخة سابقة بأنه «إشعار بانتظار المستخدم».)
4. ⚠️ **`token` في جدول المستخدم** يعني جلسة واحدة فعّالة لكل مستخدم (تسجيل دخول جديد يُلغي القديم) — وهذا **متضارب** مع قرار سابق بأن «الدخول من أكثر من جهاز عادي»، فعند بناء الجلسات سنحتاج جدول `Edu_Sessions` منفصلًا.
5. **كل فئة في جدولها المستقل:** `Edu_Users` لموظفي المنصة، `Edu_Students` للطلاب، `Edu_Parents` لأولياء الأمور — والربط بين الطالب وولي الأمر في جدول خامس `Edu_Relations`. لم تُدمج الفئات في جدول واحد لأن `role` في `Edu_Users` مخصّص لموظفي المنصة، ولكل فئة حقولها ومسار دخولها المختلف.
6. **`img_url` موجود في الجدولين** بنفس النوع والدلالة (رابط خارجي للصورة، وليس ملفًا مرفوعًا على السيرفر). لاحقًا عند رفع الملفات فعلًا، سيُخزَّن رابط الملف المرفوع في نفس العمود.

---

## 8) نقاط مفتوحة

1. خوارزمية التجزئة النهائية: **bcrypt** أم **PBKDF2 (ASP.NET Core Identity)**؟
2. مدة صلاحية الـ `token` والانتهاء (Expiry) — لم تُحدَّد بعد.
3. هل يُسمح لنفس البريد بأن يكون **مدرسًا وطالبًا** في نفس الوقت؟ (حاليًا فريد داخل كل جدول على حدة — لا يوجد قيد مشترك بين الجداول.)
4. **ولي الأمر:** هل يُنشئ له المشرف حسابًا بنفسه (مثل الطالب)، أم يُضاف تلقائيًا عند إضافة الطالب؟ ومن يدعوه؟
5. **هل يُشترط وجود ولي أمر لكل طالب؟** القاصرون نعم، لكن هل الطالب الراشد يحتاج ولي أمر؟ (القيد الحالي يسمح بطالب بلا ولي أمر.)
6. جدول **الإشعارات الحقيقي** — سيأتي عندما نحدّد: من يُشعَر، وبأي أحداث، وكيف يُقرأ الإشعار.
7. جدول **`Edu_Sessions`** — للسماح بالدخول من أكثر من جهاز، وإلغاء الجلسات.
