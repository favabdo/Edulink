## 1) الستاك المقترح

| الطبقة | الاختيار | الحالة | السبب |
|---|---|---|---|
| قاعدة البيانات | **SQL Server** | ✅ مؤكد | اختيار صاحب المشروع صريحًا |
| الباك إند | **ASP.NET Core (.NET)** | 🔶 توصية | يتكامل أصلًا مع SQL Server، أداء عالي تحت الضغط والـ concurrency، يعمل على Linux VPS رخيص، ويسهّل توجيه كل مؤسسة لقاعدة بياناتها حسب الدومين |
| الفرونت | **React + TypeScript** | ✅ مؤكد عمليًا | المشروع مُهيَّأ فعليًا على Vite + React + TypeScript، والـ SPA مناسب لتطبيق فيه فيديو عالي الأداء و RTL/LTR |
| الفيديو / اللايف | **LiveKit** (SFU مفتوح المصدر) | 🔶 توصية | يتوسّع أفقيًا، يشيل آلاف الـ tracks، عنده simulcast + TURN، والـ client سهل مع React |
| السبورة البيضاء | **Excalidraw** | 🔶 توصية | مفتوح المصدر (MIT)، يندمج بسهولة مع LiveKit |
| الاستضافة | **ألمانيا — Hetzner** | ✅ مؤكد | اختيار صاحب المشروع، والمستخدمون من كل العالم |

**بديل الباك إند لو أراد صاحب المشروع لغة واحدة في المشروع كله:** Node.js (NestJS) — لكن `ASP.NET Core` أقوى أداءً وتكاملاً مع SQL Server للنطاق المطلوب.

**بديل الفيديو:** `mediasoup` (أخف لكن تبني كل شيء حوله بنفسك) — أو خدمات SaaS مدفوعة (`Zoom SDK`, `Daily.co`, `100ms`, `Agora`) وهي أسرع لكن بتكلفة مستمرة وارتباط بمزوّد. القرار: **نبني عندنا** لتجنّب التكلفة المستمرة والارتباط.

## 2) واقع هدف «1000 سيشن متزامنة» — أرقام يجب تذكّرها

هذا الرقم **هدف مستقبلي**، وليس الحاجز الحالي (الحالي: **بالمئات**). لكن التصميم لازم يكون **قابلًا للتوسّع أفقيًا من أول يوم**.

الحساب الواقعي:

- كل سيشن 1-to-1 بجودة كويسة ≈ **2.5 – 3 Mbps**.
- **1000 سيشن ≈ 2.5 – 3 Gbps ثابت**.
- شهريًا ≈ **20 – 30 TB نقل بيانات**.

النتيجة العملية:

- سيرفر واحد لا يكفي — نحتاج **عدة LiveKit nodes** موزّعة على ريجنات (أوروبا + أمريكا + آسيا) + **TURN server** للشبكات الضعيفة.
- **الخطة الصحيحة:** الكود يُكتب من الأول بحيث يقبل التوسّع الأفقي، لكن **عدد السيرفرات يتزايد مع الطلب الفعلي** — نبدأ بنود واحد، ونعمل اختبار ضغط (stress test) عند كل milestone، ونضيف nodes لما الإحصائيات تطلب. كده نوصل لأعلى كوالتي بأقل تكلفة واقعية.

## 3) ملاحظة الترخيص — مهمة جدًا لأن المنتج يُباع

المنصة **مقفولة المصدر** وتُباع لمؤسسات. لذلك:

- ✅ **آمن:** `Apache-2.0` و `MIT` — ومنها **LiveKit** (Apache-2.0) و **Excalidraw** (MIT).
- ⚠️ **يُلزمك بنشر الكود:** `GPL` / `AGPL` — ومنها **Cal.com** (AGPL-3.0)، **Moodle**، **Canvas**، **Open edX**.
- **القاعدة:** لو هنستخدم مكوّنًا أساسيًا في المنتج، يكون Apache/MIT. المكونات GPL/AGPL تُستخدم **كمرجع للأفكار وتصميم قاعدة البيانات فقط** ولا تُدمج في الكود.

## 5) قرارات معمارية ناتجة عن المتطلبات

### أ) توجيه المؤسسة (Tenant Resolution) بالدومين

كل مؤسسة لها **دومين خاص + قاعدة بيانات مستقلة** ونفس الـ backend. فالمطلوب طبقة middleware:

1. تقرأ الدومين من الطلب.
2. تحدّد المؤسسة (من قاعدة بيانات مركزية صغيرة تحفظ الـ tenants وconnection strings).
3. تفتح سلسلة الاتصال بقاعدة بيانات المؤسسة دي.
4. تابع الطلب.

> ملاحظة: كلمة **tenant** هنا تعني «مؤسسة»، وكل مؤسسة قاعدتها منفصلة — أي **قاعدة بيانات لكل عميل**، وليس صفوفًا متعددة داخل نفس القاعدة.

### ب) نموذج المواعيد (Recurring + Exceptions)

المطلوب أسبوعي متكرر + حصص تعويضية + إلغاء، فالبنية لازم تفصل بين:

- **نمط الجدول الأسبوعي** (weekly schedule pattern).
- **الحدوث الفعلي لكل حصة** (session occurrence) — وهو الكيان اللي بيتسجّل عليه الحضور والمدة والحالة.

### ج) الـ i18n من أول يوم

عربي + إنجليزي **معًا**، بنظام dictionaries وتبديل اتجاه RTL/LTR — **ممنوع** كتابة نص عربي/إنجليزي مباشرة داخل المكوّنات.

### د) الفيديو والـ metadata

- **لا تسجيل للسيشنات.** يُحفظ فقط: المدة، وقت البداية والنهاية، الحضور، والحالة.
- LiveKit يدعم التسجيل (`Egress`) — **لن نستخدمه**، ويُفضّل تعطيله من إعدادات السيرفر لتفادي أي تسجيل غير مقصود.

### هـ) الملفات والوسائط

مطلوب: صور + ملفات + فيديوهات (ملفات مساعدة يرفعها المدرس).

- **التوصية:** تخزين الملفات في **مساحة ملفات / تخزين كائني**، وقاعدة البيانات تحفظ **الـ metadata والمسار فقط**، مع تصميم يسمح بتبديل مزوّد التخزين.
- تخزين الفيديو داخل SQL Server ممكن تقنيًا لكنه غير مُستحسن (أداء + حجم النسخ الاحتياطي). القرار النهائي لصاحب المشروع — وهو قال إنه متقبّل للاحتمالين.

## 6) نقاط لسه محتاجة تأكيد قبل الكتابة

1. **تأكيد الباك إند:** `ASP.NET Core` نهائيًا؟
2. **تأكيد LiveKit** كمحرّك الفيديو.
3. **وجهة تخزين الملفات:** مساحة ملفات أم داخل SQL Server.
4. تفاصيل **الصلاحيات** لكل دور (صاحب المشروع قال هيتكلم عنها لاحقًا).
5. هل المنصة تحتاج **إشعارات** (إيميل / Push / تذكير قبل الحصة)؟ — لم يُحسم بعد.
6. منطقة **توقيت** الحصص والتعامل مع المستخدمين في دول مختلفة (التخزين UTC والعرض محليًا) — لم يُحسم بعد.
